## Context

This change turns the phase-1 Windows build into a supported platform (see [proposal](./proposal.md)).
The constraints that shape the design:

- Linux and macOS behavior must not change. Every Windows difference is behind `cfg(windows)` or `cfg(unix)`.
- All crates use `#![forbid(unsafe_code)]`, so Win32 APIs are reachable only through safe crates
  (`windows-service`, `tokio::signal::windows`) or through system tools (`taskkill`, `icacls`, PowerShell).
- The MQTT broker is external. thin-edge.io does not ship one, on Linux or on Windows.
- Packaging (MSIX) and the winget plugin are owned by the `windows-msi-packaging` and `windows-sm-plugin` changes.
- CI has no Windows container image for thin-edge.io, and Windows containers cannot run the Linux image used by the Robot Framework suite.

## Goals / Non-Goals

**Goals:**

- Every component either works on Windows or fails with an explicit "not supported on Windows" error.
- Clean service stop: health `down` published, MQTT sessions closed, lock files released.
- No orphan processes after a workflow, plugin or custom-operation timeout.
- Child devices work on Windows, including their `operations/c8y/<xid>` directories.
- Private keys and credentials are not readable by non-administrators.
- `cargo clippy -D warnings` and the unit tests pass for `x86_64-pc-windows-msvc` in CI.
- A Robot Framework suite runs against a real Windows host in CI.

**Non-Goals:**

- Porting `shell_execute` (`tedge-shell-plugin`). It depends on process groups, `flock` and `poll` on a pipe; a Windows design needs ConPTY or job objects and is a separate change.
- PKCS#11 socket proxy over named pipes. Direct cryptoki access works on Windows; the proxy stays Unix-only.
- The Mosquitto bridge configuration generated by `tedge connect` (`mqtt.bridge.built_in = false`). It writes `/etc/tedge/mosquitto-conf` and restarts mosquitto through the init system. The built-in bridge replaces it on Windows.
- Running the existing Linux Robot Framework suites on Windows. Only a dedicated Windows suite is in scope.
- Fine-grained ACLs per file (per-user ownership mapping of `user`/`group`/`mode`).

## Decisions

### D1 — Shutdown requests are a supervisor command, not a signal

`tedge_supervisor` exposes `request_shutdown()`, backed by a static `tokio::sync::Notify`.
The signal listener selects on it next to the OS signals and turns it into `Command::ShutdownAll`.
On Windows the listener also selects on `ctrl_c`, `ctrl_break`, `ctrl_close` and `ctrl_shutdown`.

The Service Control Manager calls the control handler on its own thread.
On `Stop`/`Shutdown` the handler reports `StopPending` with a 30 s wait hint and calls `request_shutdown()`.
When the service's runtime returns, `service_main` reports `Stopped` with the exit code.
A watchdog thread exits the process after 30 s if the drain hangs.

Alternative rejected: `std::process::exit(0)` in the control handler (phase 1).
It skips the supervisor drain, so the health status stays `up` and the MQTT session is not closed.

`Notify::notify_one` stores a permit, so a stop request that arrives before the listener is registered is not lost.

### D2 — `tedge run all` is a service like the others

`windows_service_name()` maps a parsed command line to its service name:
`tedge run all` → `tedge`, `tedge-agent` → `tedge-agent`, `tedge-mapper <cloud>` → `tedge-mapper-<cloud>`.
The same function drives the dispatcher in `main` and the SCM registration in `service_main`.
This keeps one place that decides which commands can run under the SCM.

### D3 — Process trees are terminated with `taskkill /T`

Unix starts commands in their own process group and signals the group.
Windows has no process groups usable without `unsafe`, but `taskkill /T /PID <pid>` walks the process tree.

- Graceful step: `taskkill /T /PID <pid>`. GUI processes receive `WM_CLOSE`.
  Console processes cannot be asked to close: `taskkill` then fails, and the tree is terminated with `taskkill /T /F` immediately.
- Forceful step: `taskkill /T /F /PID <pid>`, for what is left of the tree.

This is implemented once in `tedge_utils::signals::terminate_process_group` (used by `LoggedCommand`)
and in `tedge_script_ext` (which does not depend on `tedge_utils`).

Alternative rejected: Job objects. They give stronger guarantees (no escape by re-parenting)
but need `unsafe` Win32 calls or a new dependency, and the gain does not justify either for timeouts.

A process killed with `taskkill /F` exits with code 1, like a failure.
The script runner records that it killed the process and reports exit code `0xC000013A` (`STATUS_CONTROL_C_EXIT`) instead;
`tedge_utils::signals::killed_by_signal` maps this code to SIGKILL, so workflows take their `on_kill` transition on both platforms.

Consequence: a console script cannot react to the graceful step: on Windows it is killed when the graceful timeout expires,
without the forceful timeout extension a Unix script gets to clean up after SIGTERM. This is documented as a difference.
Waiting for the forceful timeout instead would let a 3 s workflow timeout run for more than a minute,
since the forceful extension is at least 60 s.

### D4 — One plugin discovery rule, in `tedge_utils::plugins`

`plugin_name(path)` returns the file stem on Windows and the file name elsewhere.
`is_plugin_candidate(path)` accepts any file on Unix, and only the extensions
`exe`, `bat`, `cmd`, `ps1`, `com` (case-insensitive) on Windows.
`plugin_sm`, `tedge_log_manager`, `tedge_config_manager` and `tedge diag collect` use these functions.

Scripts are launched by `SudoCommandBuilder::command`, which already maps
`.bat`/`.cmd` to `cmd.exe /c` and `.ps1` to `powershell.exe -NoProfile -ExecutionPolicy Bypass -File`.
`sudo` is never used on Windows: services run as `LocalSystem`.

### D5 — Child-device directories use percent-encoding on Windows

External IDs such as `main:device:child1` contain `:`, which is invalid in Windows file names.
On Windows the directory name is the external ID with `%`, `<`, `>`, `:`, `"`, `/`, `\`, `|`, `?`, `*`
encoded as `%XX` (upper-case hex). `xid_from_path` decodes the name back.

- Reversible, so `xid_from_path` keeps working without a lookup table.
- `%` is encoded first, so a literal `%3A` in an ID cannot be confused with an encoded `:`.
- Linux keeps raw directory names: existing devices and scripts that create these directories are unaffected.

Alternative rejected: replacing `:` with `_`. It is not reversible (`a_b` and `a:b` collide).

### D6 — Access control at the directory level

On Linux, ownership (`tedge:tedge`) and modes (`0o600` for keys) protect secrets.
On Windows the equivalent is an ACL on `C:\ProgramData\tedge`, inherited by every file below it:
`SYSTEM` and `BUILTIN\Administrators` have full control, inheritance from `C:\ProgramData` is removed.
`ensure_windows_data_dirs` applies it with
`icacls <dir> /inheritance:r /grant:r *S-1-5-18:(OI)(CI)F *S-1-5-32-544:(OI)(CI)F`
when the directory is first created, and the installer applies it on install.

- SIDs instead of names, because group names are localized (`Administratoren` on German Windows).
- Applied once at creation, so an administrator can relax it afterwards without it being reverted.
- The `user`/`group`/`mode` fields of permission entries stay no-ops on Windows. Mapping Unix owners to Windows principals is out of scope.

Alternative rejected: per-file ACLs on the private key only.
The credentials file, `tedge.toml` and the entity store also need protection, and a directory ACL covers all of them.

### D7 — Unsupported features fail explicitly

- `tedge-shell-plugin` and `tedge-p11-server` compile to a `main` that returns "not supported on this platform".
  Their library code is `cfg(unix)`, and the `tedge-shell-plugin` multicall entry is removed on Windows.
- The agent does not register `shell_execute` on Windows, whatever `agent.enable.shell_execute` says,
  so the mapper never declares `c8y_Command`.
- SIGHUP (log level reload) and SIGUSR1 (mapper restart) have no Windows equivalent;
  `Restart-Service` covers both.

### D8 — Robot Framework runs on the Windows runner itself

The Linux suites use the `docker` adapter and a Debian image with systemd and a Mosquitto logging plugin.
Windows containers cannot run that image, and a Windows container image with services is a 3–5 GB pull per job.
The GitHub `windows-latest` runner is an ephemeral VM, so tests run on the host with the `local` adapter:

- The `local` adapter of `device-test-core` is POSIX-only (`sudo`, `env`, `/bin/sh -c`, `tar`).
  `ThinEdgeIO` registers a Windows variant when `os.name == "nt"`:
  commands run through `powershell.exe -NoProfile -NonInteractive -Command`,
  environment variables are passed to `Popen`, `copy_to` uses `shutil`.
  The variant lives in `tests/RobotFramework/libraries/ThinEdgeIO/windows_adapter.py` until it is upstreamed to `device-test-core`.
- MQTT assertions on Linux read the log of the `mosquitto-log-plugin`, which has no Windows build.
  On Windows, `ThinEdgeIO` starts a paho-mqtt subscriber to `#` during `Setup` and records every message with its timestamp.
  `mqtt_match_messages` filters these records with the same arguments as `mqtt-log`.
  Retained messages delivered on subscription are recorded with the subscription time.
- Windows tests are tagged `platform:windows` and live in `tests/RobotFramework/tests/windows/`.
  Linux runs exclude the tag; the Windows job includes only it.
- Cumulocity tests use the same `.env` secrets as the Linux jobs and are skipped when the secrets are absent (forks).

Alternative rejected: the `ssh` adapter against a Windows VM. It needs long-lived infrastructure and OpenSSH on Windows; the ephemeral runner provides a clean machine per job for free.

## Risks / Trade-offs

- [Console scripts get no chance to clean up on timeout] → Documented; they are killed at the configured timeout, as a user expects.
- [`taskkill` can miss a child that re-parented before the kill] → Rare for plugin scripts; job objects remain an option.
- [Directory ACL locks out non-admin users who used `tedge` before] → `tedge` CLI on Windows already needs an elevated shell to manage services; documented in the install guide.
- [Percent-encoded directory names surprise users creating child-device directories by hand] → Documented with an example; Linux behavior is unchanged.
- [The paho recorder misses messages published before `Setup`] → Same as `mqtt-log` filtering by test start time; tests only assert on messages after `Setup`.
- [Windows CI adds ~25 min per pull request] → Runs in parallel with the Linux jobs; Robot suite limited to Windows-specific coverage.
- [Monkey-patching the `device-test-core` local adapter breaks on an upstream refactor] → The variant is a subclass with a pinned `device-test-core` version; upstreaming is a tracked task.

## Migration Plan

No migration on Linux.
On Windows, phase-1 installs that created `operations/c8y/<xid>` directories could not contain `:`, so no existing directory needs renaming.
The ACL is applied only when `C:\ProgramData\tedge` is created; existing installs get it from the installer on upgrade.

## Open Questions

- Should `tedge-mapper-c8y` keep a separate service, or should the MSIX package register only `tedge` (`tedge run all`)? This change supports both; the default belongs to `windows-msi-packaging`.
